# Publication and maintenance

The canonical CI is a first deployment on a fresh feed. See [setup and rollout](setup.md) before activation and [orchestration/recovery](ci-orchestration.md) for execution details. No old capture, package history or bootstrap release is used.

Sources own matrices, dependencies, build commands and packaging hooks in their version-tag commits. DP's allowlist permits them; their own first verified tag notification activates them. `ci.repository.PROJECTS` is a derived pinned runtime view, not a central product authority. A source release never implicitly builds prerequisites. Missing published prerequisites fail affected rows while retaining activation.

Direct releases use the exact moved/created tag. Cascades choose each active dependent's highest semantic tag, recursively per row, waiting for in-cascade joins. Distinct versions coexist in one feed, with the latest published revision for each. Fresh counters increase globally; registered row/version claims and accepted publications remain monotonic. Cascade captures with matching release provenance may share a number across rows; abandoned unregistered reservations are not a monotonic history. Same-version older revisions/attempts cannot overwrite newer. Old version support duration is not automatically decided by this CI.

Status pages show only the highest requested/captured semantic version. A new higher failure stays visible. Older direct bug-fix builds still sign and publish but do not change the displayed state, timestamp, availability or source-job link. Internal ledger events and receipts continue recording them. Unpublished higher versions do not borrow older availability.

Signing and authoritative publication remain in DP. Source credentials are coordinator/own-source readers and coordinator-only notify writers; never distribute the coordinator key or signing keys. The coordinator App key has broad installation authority even though capture/publisher/control steps request narrowed tokens. The observer needs all-org metadata and Actions reads. Anyone holding notify Actions:write retains cancellation/artifact-deletion denial-of-service ability. Credential provisioning/scoping/rotation are separate operator stages.

Ownership is the pinned `package` namespace at each recorded source commit. Only minimal ownership facts are read for retained files, not the full historical build schema. Source jobs receive those facts in the coordinator request and verify exact commits before reuse. Retained sources must remain registered/readable: removing access or changing the ownership contract can block rows. No migration or offboarding policy is added.

APT, RPM and OpenWrt signatures are verified against `keys/apt.asc`, `keys/opkg.pub`, and `keys/apk.pem`. There is no legacy key alias. Feed key bytes come from the deployed default-branch overlay; captured family keys must match before signing. See the [key authority and rotation procedure](ci-orchestration.md#public-key-authority-and-operating-limits). No key rotation is performed by a code correction. Local checks may use disposable fixture keys; no test provisions or rotates production credentials.

The public feed writer remains serialized and uses parentless snapshots with force-with-lease. A conflict with feed changes fails closed; status-only conflicts are merged without losing unrelated facts. Status reservations/registrations use parented CAS commits and must fail on exhaustion. Rendering is separate and best-effort. A replayed verified receipt causes no second signing or feed write.

Inventory-driven cleanup retains unreferenced packages and by-hash files for 30 days. Referenced supported versions and SDK exports remain indexed. Never delete files based only on directory age. Use the runbook for a fresh feed; initialization is a separately reviewed normal commit and revisions restart at r1, with possible downgrade effects for old installations.

The product hooks retain their existing application test coverage. Local coordinator tests do not establish successful compilation on every target, live callback latency, GitHub pool behavior or unavailable OpenWrt signatures. Recovery uses the controller's supported retry path, verified receipts and bounded reconciliation; consult the node category/reason rather than treating a public page as execution authority.

Admitted cascade capture failures carry a verified `capture-result-{attempt}` artifact. Temporary source reads retry through the existing node observation deadline and build budget; deterministic or unverifiable results require operator retry. No earlier version is substituted and publication retries are not spent.

Direct notification slots remain the sole activation authority; cascade revisions never overwrite them. Supersession is scoped to project, target and version, and requires row coverage. Pending reservations defer. Only highest-current prerequisite receipts initiate cascades. One shared arm gate prevents early joins across overlapping roots at capture, build and publication. Deterministic failed nodes retain their reasons and budgets; new baseline recovery uses a fresh highest-tag capture whose revision follows the conditional sharing rule in orchestration. A shared number means equal reservation-time release provenance, not equal bytes or later stale-rebuild inputs. Global status labels show the source version; each row shows its own package revision. Authored guides refresh independently of highest-version display fields.

The trusted publisher validates internal namespace, version/revision and architecture for every own or retained package before indexing; opkg paragraphs derive from those verified controls. Do not remove repositories with request records. See [orchestration](ci-orchestration.md) for prospective-graph CAS validation, terminal job outcomes, uncertain capture recovery and immutable baseline availability limits.
