# CI orchestration

## Ownership and invariants

[`ci/projects.json`](../ci/projects.json) contains participating repository names and optional policy settings. Every source owns `ci/packages.json`: its title, unique package prefix, `depends_on`, complete matrix and paths to its build hooks. The coordinator fetches definitions at exact commits and compares the notified JSON with the pinned source bytes. It has no central target inventory or product recipes. Central support covers runner/emulation mapping, signer formats, validated target vocabulary, feed paths and reusable tooling. Source JSON cannot introduce executable coordinator code.

Each target advances independently. Admission waits for all its transitive prerequisite publications, including every in-cascade arm of a diamond. Immediately before signing/publication, dependency source identities, revisions and owned file checksums are checked again against the current feed and the build's pinned baseline. These checks have different lifecycle responsibilities and share dependency identity calculations. Old dependent packages remain visible during rebuilding; there is no graph-atomic promotion.

The serialized `package-publication` writer and Git leases preserve atomic feed updates and unrelated products. Monotonic revisions and source attempts prevent older packages overwriting newer ones. Authenticated artifact receipts make identical replay a no-op and reject conflicting bytes under the same identity. Signers verify APT InRelease/Release.gpg, RPM packages/repomd and OpenWrt usign/APK signatures against `keys/`. Feed URLs, the legacy `snodec-usign.pub`, by-hash retention and 30-day inventory-driven cleanup remain stable.

## Release and callback contract

1. A source version-tag push invokes `notify-release.yml`, sending repository, tag, exact commit, originating run and full repository JSON through `workflow_dispatch`. Tag movement is permitted; each new capture reserves a new monotonic revision. Ordinary branch pushes do not build packages.
2. Intake verifies origin repository, workflow, push event, tag and SHA. Captures are serialized per source repository; the latest explicit request is recorded by originating request time (numeric source run ID breaks equal-time ties), not semantic version. Duplicate source-run notifications do not reserve again.
3. Capture archives exact source commits and recursive submodules, pins the tooling commit, and records per-target definitions, source identities, revision allocations and checksums. A retry cannot silently replace an expired capture. Selected definitions include their pinned JSON digest.
4. A bounded controller dispatches one source workflow per ready target. Its request carries capture, repository, target, runner, pinned Packages commit and unique dispatch intent. `return_run_details` binds the source run; ambiguous responses are reconciled by the unique title and App actor. No public CDN endpoint grants a build permit.
5. The source wrapper runs its own hooks through the reusable build workflow, uploads unsigned packages and calls back with source run, attempt, actual job ID and artifact ID/digest. The publication workflow also requires the coordinator App actor; manual retry and guide publication share a human DP-write authorization check. Authorization checks the actual triggering actor as well as the original publication actor; a notify App cannot borrow an earlier actor’s authority through rerun. Its Actions-write still permits denial of service through cancellation or artifact deletion. The callback is a claim: DP verifies GitHub run, actor, workflow, attempt, job and artifact facts and the immutable capture. A DP signature attests that the packages came from a run in that source repository, including wrapper-added jobs; it does not attest an exclusive DP recipe or SLSA proof.
6. DP dispatches central signing/publication for each artifact. The receipt records source run/attempt/job, artifact ID/digest, capture, tooling and dependency publication commit. Sign-time dependency checks reject stale packages; successful publication unlocks matching dependent targets recursively.

Ordinary cascades rebuild the dependent version last published **on that target**, using JSON at that exact commit. A never-published dependent is skipped for that target. A newer outstanding explicit request takes precedence, retaining its exact source commit even when a later cascade allocates a higher revision. Pending requests coalesce by latest request time. In-flight work is not cancelled: obsolete output is discarded or rejected and, with overlap rebuilding enabled, admitted against the new prerequisite. Overlap rebuilds have prerequisite cause. Backward tag moves preserve new-capture/new-revision behavior; no additional backward-move policy is imposed.

## Admission and capacity

Priority is ready publication, then prerequisite-triggered builds, then tag-triggered builds. Graph position never classifies priority. There is no fairness injection or preemption. Drain arguments assume bounded arrivals and retries. Sources with dependencies can still be ordinary tag-triggered releases. Builds do not wait for a full matrix.

By default capacity comes from the documented organization-plan mapping (Free 20, Pro 40, Team 60, Enterprise 500). The observer enumerates all organization repositories, including private ones, and their running workflow jobs. Only hosted jobs actually `in_progress` with an allocated runner are occupied; queued work is reported separately and does not consume occupied capacity. The implementation conservatively counts all hosted jobs against one total, including standard x64 and arm64. Self-hosted jobs do not consume this hosted pool. Larger/macOS limits are not separately scheduled by this CI.

DP's admitted source and publisher intents hold one pending commitment while `waiting` is true, even after local supersession, failure or exclusion. An observed allocated job replaces that commitment with occupancy; terminal execution also releases it. A known queued run remains committed without a deadline. An unbound intent retires only after a successful no-match listing beyond the existing 30-minute ambiguity window. Failed listings, scope failures, 404s and malformed observations never establish absence. A run that first appears after verified post-window absence is counted once occupied; this remaining underestimate is best-effort. Unrelated queued backlog does not indefinitely block admission. The controller's own running slot is already observed. Builds leave two free slots by default; publication may consume this headroom, avoiding self-deadlock. This is best-effort: count-then-dispatch is not atomic and unmanaged workflows can consume headroom. It is not an enforceable GitHub reservation.

Unknown plan, inaccessible repositories, truncated listings, missing runner allocation, timeout or API failure admit no new capacity-consuming work, including publication. Already-built artifacts remain queued. Callback verification and status reconciliation can still retain their facts. Observation failures record a bounded exponential retry delay of 1–30 minutes (including bounded server retry hints); a later scheduled/event wake retries after that deadline. A manual controller dispatch clears the cooldown after operator repair. Configuration/scope errors require operator correction; exceptions report an actionable failing endpoint. No failure is interpreted as zero occupancy or unlimited capacity.

## Observer cost

A capacity observation costs one `orgs/SNodeC` call + ⌈repositories/100⌉ inventory pages + five status listings per repository and any additional pages + a jobs listing per active run and its additional pages. For 43 repositories that is at least 217 calls before active-run jobs or node reconciliation. Capacity observation runs on control wakes with candidates once `retry_at` permits it; the optional busy-publisher optimization is not implemented.

Reconciliation adds, for each non-published waiting node (including terminal scheduling nodes), one bound-run lookup and up to one jobs listing with pagination, or one paginated `locate()` listing for an unbound intent. Completed terminal executions need only the run lookup; an artifact already awaiting publication does not repeatedly fetch completed source jobs. Each node honors its own observation deadline. Transient failures back off up to 1800 seconds with bounded `retry_after`; configuration failures retry after 1800 seconds. Unknown capacity fails closed. The observer token's real rate limit, visibility and throughput effects remain live hypotheses; no recovery timing is promised.

## State and recovery

Admission uses the existing CAS-written `Packages/status.json`, read through Git/API rather than CDN gating. `runs` owns per-capture/per-target nodes; target/timeline presentation is derived. Publication manifests/receipts own publication facts. Captured definitions in generation context support presentation after artifact expiry; runtime `ci/definitions.json` is derived and ignored by Git.

The ledger persists exact capture selections/hashes/revisions; the latest explicit request (moved tags otherwise lose intent history); dispatch intents and request baselines (needed after ambiguous transport); selected source run/attempt/job/artifact; dependency binding; separate build/publication dispatch counters; and the latest capacity failure/backoff deadline, which GitHub does not retain for this observer. GitHub supplies execution facts and manifests supply publication facts. Neither status pages nor callbacks authorize publication. No separate public permit or controller database exists.

`pending`, `running` and `publishing` are active. `published`, `superseded`, `skipped`, `unsatisfiable`, `failed` and `cancelled` close a node. Missing prerequisite row/publication is `unsatisfiable` with a reason; unpublished dependents are `skipped`. Failed prerequisites skip blocked descendants without affecting independent targets. Structural exclusions close permanently. Recoverable blocks reopen only after their prerequisite fingerprint changes. With overlap disabled, an obsolete binding closes with an explicit re-request reason. Receipts recover published facts without downloading captures. Completed source jobs are not repeatedly listed while their artifact awaits publication. Source and publication dispatch budgets are separate (three each); an operator retry resets them and reuses an artifact only while it remains available. Expired artifacts restart the source build; an expired immutable capture needs a new explicit request. Deterministic execution failures require operator retry. A node’s transient API or download failure records bounded backoff without consuming dispatch budgets or closing unrelated work.

Callbacks drive normal flow. `workflow_run` completion wakes cover DP captures and publishers; source callbacks cover builds. A single pass also reconciles missing/out-of-order callbacks against GitHub. The static ten-minute Actions schedule provides bounded rechecks when unrelated org jobs finish; passes with no candidates skip capacity observation. Each control job downloads its active captures again; completed nodes with unchanged prerequisites do not need those bundles. Terminal non-published nodes with `waiting` true still reconcile execution facts after their observation deadline, without changing scheduling status, artifacts or budgets. GitHub offers no cross-repository workflow-completion event subscription for all unmanaged jobs. There is no permanent polling loop or external service. Scheduled starts can be delayed or dropped; recovery latency is an unmeasured hypothesis, not an SLA.

Operator recovery uses **Coordinate package builds** on DP main. Dispatch with no inputs to reconcile; use `retry: capture/project/target` for a repaired terminal or unobservable node. First inspect failed capture/source/publication logs and scope errors. An expired immutable capture requires a new explicit release request, not recapturing the old generation. Do not rerun or dispatch any live workflow without authorization. See [setup](setup.md#banner) for credential and cutover stages.

## Supported policy settings

Missing settings use the defaults below. Unknown settings, matrices, graphs or commands in the master fail validation. No priority, diamond-bypass, fairness or work-conserving flag exists.

| Setting | Default | Supported alternative |
| --- | --- | --- |
| `capacity` | `"plan"` | Integer at least 3 |
| `headroom` | `2` | Positive integer below an explicit capacity |
| `dependent_version` | `"published"` | `"latest"` (max `vMAJOR.MINOR.PATCH` tag) |
| `rebuild_overlap` | `true` | `false` (explicit re-request required) |

Example: `{"repositories":["snode.c","mqttsuite","snode.c-idp"],"settings":{"headroom":2}}`. Diamond joins remain mandatory: neither A nor C establishes an agreed alternative worth a flag. Working throughput interpretation is no batching and no end-to-end target; the original compound answer remains provisional.

## Local verification

```sh
mkdir -p /tmp/codex/build/snodec/package-ci
PYTHONPATH=tests:. TMPDIR=/tmp/codex/build/snodec/package-ci \
SNODEC_TEST_TOOLING=/path/to/local-navigation-tooling \
python3 tests/run_package_checks.py --actionlint /path/to/actionlint \
  /path/to/snode.c /path/to/mqttsuite /path/to/snode.c-idp
```

`SNODEC_TEST_TOOLING` must point to a read-only checkout containing navigation tooling for local-only presentation fixtures. The runner uses isolated runtime definitions, a file-only Git protocol guard and a GitHub transport rejection shim, including renderer subprocesses. Tests use bare Git fixtures and mocked GitHub transport; they cannot establish live permissions, dispatch propagation, pool behavior or recovery latency. Actionlint exclusions are limited to its old App-token schema (`app-id`/`client-id`) and unsupported `queue` key. No live workflow dispatch is part of local verification.

## Durable capture and recovery boundaries

Reservation records explicit intent, including moved tags, before capture. Capture initialization is a required CAS transaction and never renders pages. A provisional capture retry may refresh revisions once per attempt until a capture is saved; a saved capture remains immutable. Successful registration re-enables its matching retried intent. Pending prerequisite reservations block later dependent admission before their immutable capture is registered, and a newer explicit reservation suppresses older work for that product. The controller observes reserved captures that never registered a generation and marks completed failed captures ineligible; an older capture cannot invalidate a newer request. A selected dependent’s capture error stays in its row profile and closes that dependent without stopping the prerequisite. Presentation uses recorded selected-source and feed facts, including rows retained from older captures.

Build and publication dispatch share encoded intent/actor lookup. A transport-ambiguous request retains its commitment for up to 30 minutes; a short listing absence never triggers automatic redispatch. After that bound the task reports an actionable unresolved dispatch and retains its commitment until an operator inspects and retries it. Operator retries can create duplicate executions if GitHub accepted an earlier invisible dispatch; publication identity and stale checks still protect the feed. Definitive dispatch rejections release their commitment.

Control uses the finite `queue: max` queue (up to 100 pending runs); this is not guaranteed delivery. GitHub state recovers lost callbacks, while a lost manual operation needs re-requesting. Node observation failures are scoped and classified; organization capacity observation remains globally fail-closed. The ten-minute scheduled wake can be delayed, dropped, or disabled after prolonged public-repository inactivity; manual recovery remains required. No measured latency guarantee is claimed.

The running control job consumes headroom rather than reserving its own slot twice. Pending commitments expire when their known execution is terminal; unresolved dispatch intents retain a commitment until resolved or explicitly retried. Node failures are reported in `status.json` under `runs[capture].nodes[target/project].observation`, with category, reason and retry time; inspect that record alongside workflow logs when repairing scope or transport failures.

The observer lists all five nonterminal run states (`queued`, `waiting`, `pending`, `requested`, `in_progress`), then inspects actual jobs. Aggregate run state never proves job occupancy. With 43 visible repositories, the inventory and first run-list pages cost 217 API requests plus job-list pages; this is a scaling cost, not a measured latency. Immutable JSON lookups are shared only within one CLI process/wake, keyed by exact SHA. There is no persistent definition cache. A successful source completion without a visible receipt gets three bounded observation rechecks before requiring operator recovery.

Publication restores sibling bytes from the current feed and retains their recorded source/tag/version facts. Retained sources must remain registered and readable. A retained sibling with no usable pinned ownership definition is rejected before signing or feed mutation; restore that definition before retrying. Unpublished repositories with invalid heads do not obstruct publication. Historical feeds without source JSON therefore need ownership validation during the proposed cutover, rather than assuming bootstrap preservation can be inferred from package filenames.

Readiness and dispatch use the same immutable Packages commit and dependency binding, even if an intervening ledger CAS refresh observes a newer feed. Any dependency publication after that snapshot is checked again at publication and causes safe re-admission; it cannot silently change the dispatched baseline.

## Pinned ownership and request selection

The `package` namespace at each manifest source's exact commit is the ownership contract. Ownership must not depend on a capture's selected products, default branches or the historical build matrix. Coordinator and publisher resolve facts independently from the same immutable JSON lookup used for selected definitions; only the selected build view validates reserved metadata and the full build schema. Historical ownership ignores unrelated fields and validates the pinned commit and package namespace. Coordinator and publisher each use their existing read authority; source jobs receive `_commit`/`package` facts for retained baseline sources through the existing transient request definitions, plus full definitions for the prerequisite closure. Source facts must match the baseline at the dispatched publication commit. Source build credentials remain scoped to DP and the source's own repository; a missing/mismatched supplied prerequisite definition fails instead of reading a sibling repository. The former source-job API fallback is therefore unreachable.

Selection is shared between pre-reservation configure and CAS-fresh prepare. A valid explicit request supporting the row wins. Verified row omission, or a request already ineligible, permits last-published fallback. A transient selected-source read defers that row, preserves the request and never selects older source bytes; a deterministic failure excludes that row with a reason. A later capture reselects the unchanged explicit commit after access recovers. Its own captured generation also retains that source for normal replacement/overlap handling. With overlap disabled, stale work requires an explicit re-request. These policies do not mutate immutable captures or add a separate pending queue.

Observation categories and reasons are in `status.json`, under each node's `observation`. If an unobservable publisher stalls publication priority, or a terminal waiting node holds a known-run commitment after access is lost, inspect the recorded run and repair access first. An authorized operator can retry `capture/project/target` through Coordinate package builds; this deliberately releases the old commitment and can duplicate a still-queued execution. There is no automatic assumption that an inaccessible run disappeared and no implicit abandon operation. A 404 can mean expired or inaccessible. Configuration failures remain actionable and retry every 30 minutes. Status pages are presentation, not the execution/error authority.
